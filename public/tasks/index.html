تسک‌های تیم Front و Backend

هدف: ساختِ محصولِ واقعی مطابقِ پروتوتایپ (این سایت، cheedafar.ir). تیم Front صفحه‌ها را در Next.js می‌سازد و تیم Backend، API را در Django می‌سازد. هر تسک ریز، مستقل و اندازه‌ی یک issue است.

راهنمای نشان‌ها: انجام‌شده کار می‌کند · ناقص UI هست ولی داده mock/بک‌اند ندارد · نساخته اصلاً وجود ندارد · و اولویت: P1 پایه/بحرانی · P2 مهم · P3 بعدی.
تصویر کلی و معماری تسک‌های Front (Next.js) تسک‌های Backend (Django) نگاشت صفحه ↔ endpoint ↔ تسک

تصویر کلی و معماری

سه قطعه‌ی مستقل داریم که باید به هم برسند:

قطعهچیستوضعیت امروز
Prototype (cheedafar.ir)
motoshub-prototype		طرحِ هدف — React SPA، ۳۴ صفحه، ~۲۰ بخش، داده‌ی mock با شکلِ /api/v1کامل به‌عنوان طرح؛ داده‌اش mock است
Front (motonextfront.shub.ir)
motoshub-web-client		Next.js 16 + React 19 + TanStack Query + Zustand + axios؛ به PHP api/v1 (motonext.shub.ir) وصلفقط auth + blogs واقعی؛ بقیه UIِ mock. ~۱۳ روت گمشده
Backend (api2.shub.ir)
motoshub-new-api		Django 5.2 + DRF + SimpleJWT + drf-spectacularفقط اسکلتِ auth (۲ endpoint: /me, /health)؛ فیچرها ۱۰۰٪ نساخته
تصمیم معماری کلیدی (باید تیم‌ها هم‌راستا باشند): Front امروز به PHP api/v1 (motonext.shub.ir) وصل است. قرار است Backendِ Django همان قراردادِ api/v1 را بسازد تا بعداً بدون تغییرِ Front جایگزین شود. پس Backend باید دقیقاً همان قراردادِ REST را پیاده کند که در مرجع API و Swagger مستند است (۲۹۳ عملیات). Front هم باید طوری بنویسد که مبدأ (PHP یا Django) برایش فرقی نکند.
نکته‌ی auth (اختلاف مهم): Django فعلاً JWT مشترک نمی‌سازد — توکنِ دیتابیسِ اکسوال (ow_base_user_auth_token) را می‌خواند. Front از JWTِ PHP (/auth/login) استفاده می‌کند. این دو باید یکی شوند: یا Django همان JWT HS256 با رازِ مشترک (OW_PASSWORD_PEPPER) را صادر/تأیید کند، یا Gateway هماهنگ کند. (تسک B0.)

تسک‌های تیم Front (Next.js — motoshub-web-client)

تسک‌های تیم Backend (Django — motoshub-new-api)

هدف: پیاده‌سازیِ قراردادِ api/v1 (همان که PHP دارد) در Django، منبع‌به‌منبع. مرجعِ دقیق: مرجع API و openapi.json.

الف) پایه و زیرساخت

B0.1 P1 نساخته
استراتژی auth واحد PHP ↔ Django. تصمیم: JWT HS256 با رازِ مشترک (OW_PASSWORD_PEPPER) با claims {iat, exp, sub}. Django باید همان را verify (و در صورت نیاز صادر) کند. بلوکِ SIMPLE_JWT (الگوریتم/کلید) الان اصلاً وجود ندارد.
فایل: config/settings/base.py · مرجع: معماری بخش auth
B0.2 P1 نساخته
endpointهای auth. فقط /me و /health هست. باید: POST /auth/login, POST /auth/register, POST /auth/refresh, PATCH /auth/change-password, GET /auth/permissions.
B0.3 P1 نساخته
زیرساختِ REST مشترک. صفحه‌بندی استاندارد (data/links/meta مثل PHP)، فیلتر/جستجو/مرتب‌سازی، CORS (نصب نیست)، مدیریت آپلود فایل/رسانه، فرمتِ خطای یکسان (۴۰۱/۴۰۳/۴۲۲/۴۰۴).
B0.4 P1 نساخته
رفعِ اشکالات استقرار. config/settings/production.py خالی است؛ docker/Dockerfile ENTRYPOINT اشتباه دارد (shub.asgi, Celery SharifAutoEDA — کپی از پروژه‌ی دیگر)؛ کلیدهای .env.example برای legacy DB بدنویسی‌شده. requirements فاقد gunicorn/uvicorn/pytest/celery است.
B0.5 P2 نساخته
تصمیمِ داده: نگاشتِ جداولِ اکسوال یا مهاجرت به DB جدید. الان فقط ۲ جدول (ow_base_user, ow_base_user_auth_token) به‌صورت managed=False نگاشت شده. برای هر منبع باید تصمیم گرفت: خواندن مستقیم از جداولِ ow_ (managed=False) یا مهاجرت به motoshub_new.

ب) پیاده‌سازی منابع (هر کدام: Model + Serializer + View + URL + تست)

هر ردیف یک تسکِ مستقل است؛ باید دقیقاً با قراردادِ endpoint مربوطه در PHP api/v1 یکی باشد (همان مسیر، فیلدها، صفحه‌بندی، سطح دسترسی).
