شروع سریع

وضعیت فعلی: روی سرور تولید هنوز فقط ۲۴ endpoint قدیمی فعال است. این 281 endpoint پس از merge شدن ۹ درخواست ادغام و اجرای دستورهای استقرار فعال می‌شوند. قرارداد نهایی است — پیاده‌سازی سمت فرانت‌اند می‌تواند بر اساس همین سند آغاز شود.

آدرس پایه: https://motonext.shub.ir/api — همه‌ی مسیرها با /v1/... ادامه پیدا می‌کنند.

// ۱) ورود و گرفتن توکن
const res = await fetch('https://motonext.shub.ir/api/v1/auth/login', {
  method: 'POST',
  headers: { 'Content-Type': 'application/json' },
  body: JSON.stringify({ username: 'user', password: 'secret' })
});
const { access_token } = await res.json();

// ۲) بقیه‌ی درخواست‌ها با همان توکن
const events = await fetch('https://motonext.shub.ir/api/v1/events?page=1&per_page=20', {
  headers: { Authorization: `Bearer ${access_token}` }
}).then(r => r.json());

راه‌اندازی و استقرار

این بخش گام‌های لازم برای فعال‌سازی api/v1 روی یک محیط (محلی یا سرور) را به ترتیب اجرا شرح می‌دهد. گام‌های ۱ تا ۵ بر عهده‌ی تیم بک‌اند یا DevOps است و گام ۶ به بعد مربوط به تیم فرانت‌اند است.

الف) استقرار سمت سرور

  1. دریافت کد. پس از ادغام ۹ درخواست ادغام در شاخه‌ی اصلی، آخرین نسخه را روی سرور بگیرید: 
    git pull origin main
  2. نصب وابستگی‌ها. لایه‌ی Bridge و swagger-php از طریق Composer نصب می‌شوند: 
    composer install --no-dev --optimize-autoloader
    در صورت اجرا داخل کانتینر: 
    docker compose exec app composer install --no-dev --optimize-autoloader
  3. ثبت مجوزهای API. هر endpoint با گروه و اکشن مجوزِ خود محافظت می‌شود. این دستور گروه‌ها و اکشن‌ها را ثبت کرده و به نقش‌های موجود اعطا می‌کند. دستور idempotent است و اجرای مکرر آن بی‌خطر است: 
    php motoshub api:permissions-migrate
    برای مشاهده‌ی تغییرات پیش از اعمال: 
    php motoshub api:permissions-migrate --dry-run
    اجرا نشدن این گام باعث می‌شود همه‌ی endpointها با کد 403 پاسخ دهند، حتی برای کاربر معتبر.
  4. پاک‌سازی کش. پس از تغییر مجوزها و مسیرها، کش اکسوال باید بازسازی شود: 
    rm -rf ow_smarty/template_c/* ow_static/tmp/*
  5. راستی‌آزمایی. سلامت استقرار با دو درخواست بررسی می‌شود: 
    curl -i https://motonext.shub.ir/api/v1/docs/json | head -1
curl -i -X POST https://motonext.shub.ir/api/v1/auth/login \
  -H 'Content-Type: application/json' \
  -d '{"username":"...","password":"..."}'
    پاسخ مورد انتظار: کد 200 برای هر دو، و مشاهده‌ی 281 عملیات در خروجی docs/json. صفحه‌ی تعاملی نیز روی /api/v1/docs/index در دسترس است.

ب) اتصال سمت فرانت‌اند

  1. تعریف آدرس پایه. آدرس پایه را از متغیر محیطی بخوانید تا محیط‌های توسعه و تولید جدا بمانند: 
    // .env
VITE_API_BASE_URL=https://motonext.shub.ir/api/v1
  2. پیاده‌سازی ورود. POST /v1/auth/login را فراخوانی کرده و access_token را به همراه expires_at ذخیره کنید. با توجه به اعتبار یک‌ساعته‌ی توکن، زمان انقضا باید نگهداری شود تا پیش از سررسید، ورود مجدد انجام گیرد.
  3. ارسال خودکار توکن. یک interceptor تعریف کنید که هدر Authorization: Bearer <token> را به همه‌ی درخواست‌ها اضافه کند.
  4. مدیریت خطاها. رفتار مورد انتظار برای کدهای وضعیت:
    • 401: توکن نامعتبر یا منقضی است؛ کاربر به صفحه‌ی ورود هدایت شود.
    • 403: کاربر مجوز ندارد، یا حساب او معلق یا تأییدنشده است؛ پیام فارسیِ موجود در بدنه‌ی پاسخ به کاربر نمایش داده شود.
    • 422: خطای اعتبارسنجی؛ شیء errors شامل نگاشت نام فیلد به فهرست پیام‌هاست و باید کنار همان فیلد فرم نمایش یابد.
    • 404: منبع یافت نشد.
    جزئیات ساختار پاسخ خطا در بخش خطاها آمده است.
  5. ساخت لایه‌ی دسترسی. برای پرهیز از پیاده‌سازی دستی، کلاینت را از روی مشخصات OpenAPI تولید کنید: 
    npx openapi-typescript motoshub-api-v1.openapi.json -o src/api/schema.ts
    فایل openapi.json و Postman collection از همین صفحه قابل دریافت‌اند.
  6. کنترل نمایش بر اساس مجوز. پس از ورود، GET /v1/auth/permissions را فراخوانی کنید و بر اساس فهرست بازگشتی، بخش‌هایی از رابط کاربری را که کاربر مجاز به آن‌ها نیست پنهان کنید. این کار از دریافت 403های قابل پیش‌بینی جلوگیری می‌کند.
محیط آزمایش پیش از تولید: تا زمان ادغام درخواست‌های ادغام، تیم فرانت‌اند می‌تواند با اجرای گام‌های الف روی یک محیط محلی، نسخه‌ی کامل ۲۸۱ endpoint را بالا بیاورد و توسعه را آغاز کند. قرارداد مسیرها، پارامترها و ساختار پاسخ‌ها نهایی است و تغییر نخواهد کرد.

احراز هویت

جریان ورود

POST /v1/auth/login با username و password ارسال می‌شود و پاسخ شامل access_token (JWT)، token_type و expires_at. توکن یک ساعت اعتبار دارد؛ پس از انقضا، درخواست ورود مجدداً ارسال شود.

ارسال توکن

در هدر: Authorization: Bearer <token>
endpointهایی که با نشان auth مشخص شده‌اند بدون توکن 401 می‌دهند.

نکته‌ی مهم: حساب‌های معلق یا تأییدنشده توسط مدیر هم در login و هم در هر درخواست بعدی 403 می‌گیرند — حتی اگر توکنشان هنوز منقضی نشده باشد. پس اگر ناگهان 403 با پیام فارسی گرفتید، کاربر را از سیستم خارج کنید.

GET /v1/auth/me اطلاعات کاربر جاری و GET /v1/auth/permissions فهرست مجوزهای او را می‌دهد — برای تصمیم‌گیری دربارهٔ نمایش یا پنهان‌کردن بخش‌های رابط کاربری مفید است.

قراردادهای مشترک

افعال (verbs)

GET خواندن · POST ساختن یا اقدام · PATCH ویرایش · DELETE حذف.
رفتار PATCH در همه‌ی منابع یکسان نیست؛ بخش زیر را ببینید.

صفحه‌بندی

فهرست‌ها page و per_page می‌گیرند و q برای جستجو. مرتب‌سازی با sort_by_<field>=asc|desc (مثلاً sort_by_created_at=desc).

// پاسخ فهرست‌ها
{
  "data": [ /* آیتم‌ها */ ],
  "links": { "first": "...", "last": "...", "prev": null, "next": "..." },
  "meta":  { "current_page": 1, "per_page": 15, "total": 42, "last_page": 3 }
}

// پاسخ عملیات نوشتن
{ "status": "success", "status_code": 201, "message": "...", "data": null }
پاسخ عملیات ساخت، منبع ساخته‌شده را برمی‌گرداند. POST با کد 201 پاسخ می‌دهد و data شامل رکورد تازه است — با همان ساختاری که GET همان منبع برمی‌گرداند، فیلد‌به‌فیلد یکسان. نیازی به خواندن مجدد فهرست پس از ساخت نیست.
PATCH به‌روزرسانی جزئی است. تنها فیلدهایی را بفرستید که تغییر کرده‌اند؛ فیلدهای ارسال‌نشده دست‌نخورده باقی می‌مانند. 
// فقط عنوان را عوض کن؛ بقیه‌ی فیلدها حفظ می‌شوند
await api.patch(`/v1/events/${id}`, { title: newTitle });
استثنا: منابعی که تنها یک فیلد قابل ویرایش دارند — مانند forum/posts، messages و feed — همان فیلد را اجباری می‌دانند، چون PATCH با بدنه‌ی خالی در آن‌ها بی‌معناست.
تاریخ‌ها به‌صورت ISO-8601 برمی‌گردند و هرجا معنا داشته باشد یک فیلد *_jalali هم کنارش هست (مثلاً created_at_jalali) که می‌توانید مستقیم نمایش دهید.
