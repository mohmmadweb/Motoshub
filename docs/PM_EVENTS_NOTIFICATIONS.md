# رویدادها، تاریخچه و اعلان‌های ماژول مدیریت پروژه

این سند برای تیم بک‌اند است و از روی `src/pm/events.ts` تولید شده. پروتوتایپ دقیقاً همین منطق را در مرورگر اجرا می‌کند (`src/context/ProjectsContext.tsx`). برای دیدنش در دمو، هر پروژه ← تب «تاریخچه رویدادها» و «اعلان‌ها و خودکارسازی».

## ۱. قاعده‌ی کلی

1. هر تغییری که روی پروژه انجام می‌شود یک **رویداد** با کد ثابت می‌سازد. این کد همان `event_category` در `ProjectActivityLog` است.
2. سرور رویداد را **همیشه** در `activity_logs` ثبت می‌کند. شکل آن در بخش ۴ آمده است.
3. اگر رویداد قاعده‌ی اعلان داشته باشد، گیرنده‌ها **بر اساس نقش‌شان نسبت به همان رویداد** پیدا می‌شوند، مثلاً «مسئول تسک» یا «مسئول ریسک». نام شخص در قاعده ثابت نمی‌شود.
4. کسی که کار را انجام داده، برای کار خودش اعلان نمی‌گیرد. اگر یک شخص به چند دلیل گیرنده باشد، فقط یک اعلان برایش ارسال می‌شود.
5. هر پروژه می‌تواند قاعده‌ی پیش‌فرض یک رویداد را بازنویسی کند: روشن/خاموش، گیرنده‌ها، کانال‌ها و اولویت. هر کاربر هم ترجیحات کانال، ساعات سکوت و خلاصه‌ی روزانه‌ی خودش را دارد.
6. اولویت‌ها:
   - «کم»: فقط درون‌برنامه و خلاصه‌ی روزانه.
   - «عادی»: درون‌برنامه و رایانامه.
   - «مهم»: همان «عادی» به‌علاوه‌ی پوش.
   - «فوری»: همه‌ی کانال‌ها، از جمله پیامک، و ساعات سکوت را هم نادیده می‌گیرد.
7. رویدادهای زمان‌محور را یک **زمان‌بند روزانه** صادر می‌کند و هر کدام فقط یک بار ارسال می‌شود (کلید یکتا، مثلاً `due-soon:{task}:{due}`):
   - `TASK_DUE_SOON` و `TASK_OVERDUE`
   - `MEETING_REMINDER`
   - `MILESTONE_AT_RISK`
   - `DEPENDENCY_CONFLICT`

   `BUDGET_THRESHOLD_REACHED` زمان‌بندی نیست و بلافاصله بعد از هر تغییر در هزینه یا بودجه بررسی می‌شود.

## ۲. نقش‌های گیرنده (چه کسی)

| کلید | معنا |
|---|---|
| owner | مالک پروژه (عضو با نقش «مالک») |
| manager | مدیر پروژه |
| assignee / previousAssignee | مسئول فعلی / قبلی تسک |
| successorAssignees / predecessorAssignees | مسئولان تسک‌های وابسته / پیش‌نیاز |
| team | همه‌ی اعضا به‌جز «مشاهده‌گر» |
| riskOwner, milestoneOwner, issueAssignee, issueReporter, expenseCreator | مسئول همان موجودیت |
| sponsor | کارفرما / حامی مالی |
| finance | مسئول مالی پروژه (فیلد جدید `finance_officer` روی پروژه) |
| participants | شرکت‌کنندگان جلسه |
| mentioned | افرادی که در متن منشن شده‌اند (`@نام`) |
| subjectMember | خودِ عضوی که اضافه یا حذف شده یا نقشش تغییر کرده |
| playbookStarter | کسی که اجرای Playbook را شروع کرده |

## ۴. ساختار پیشنهادی

### رکورد تاریخچه (بدون تغییر نسبت به API فعلی، فقط کلیدهای `metadata` استاندارد شود)

```json
{
  "id": 1042,
  "user_id": "u5",
  "event_category": "TASK_REASSIGNED",
  "description": "تسک «راه‌اندازی پایگاه داده» از «علی» به «سارا» واگذار شد.",
  "metadata": { "entity_type": "task", "entity_id": 45, "old_assignee": "u7", "new_assignee": "u9" },
  "created_at": "2026-05-29T10:12:00Z"
}
```

`description` باید **فارسی و در لحظه‌ی ثبت** ساخته شود؛ اگر عنوان تسک بعداً عوض شود، لاگ قدیمی نباید تغییر کند. `metadata` همیشه `entity_type` و `entity_id` و برای تغییرات، جفت `old_*` و `new_*` دارد.

### اعلان (Notification) — جدول جدید

```json
{
  "id": 88121,
  "event_code": "TASK_ASSIGNED",
  "activity_log_id": 1042,
  "project_id": 12,
  "entity_type": "task",
  "entity_id": 45,
  "actor_id": "u5",
  "recipient_id": "u9",
  "recipient_reason": "assignee",
  "title": "تسک جدید به شما واگذار شد",
  "body": "تسک «راه‌اندازی پایگاه داده» به «سارا» واگذار شد.",
  "priority": "high",
  "channels": ["in_app", "email", "push"],
  "delivery": { "in_app": "delivered", "email": "queued", "push": "sent" },
  "link": "/projects/12?tab=board&focus=45",
  "read_at": null,
  "created_at": "2026-05-29T10:12:00Z"
}
```

### قاعده‌ی اعلان هر پروژه (بازنویسی پیش‌فرض)

```json
{ "project_id": 12, "event_code": "RISK_ESCALATED", "enabled": true,
  "recipients": ["riskOwner", "manager", "owner", "sponsor"],
  "channels": ["in_app", "email", "sms"], "priority": "urgent" }
```

### Endpointهای پیشنهادی

- `GET /notifications/?unread=true&project_id=` — اعلان‌های کاربر جاری.
- `PATCH /notifications/{id}/read/` برای یک اعلان، و `POST /notifications/read-all/` برای همه.
- `GET/PUT /projects/{id}/notification-rules/` برای قواعد اعلان پروژه.
- `GET/PUT /me/notification-preferences/` برای کانال‌ها به تفکیک دسته، ساعات سکوت، خلاصه‌ی روزانه و پروژه‌های بی‌صدا.
- `GET /projects/{id}/activity_logs/?category=&user_id=&from=&to=&entity_type=&entity_id=`. در حال حاضر این endpoint فقط صفحه‌بندی دارد و فیلتر ندارد.

## ۵. نکاتی که در API فعلی (api2.shub.ir) دیدم

1. **enumها برچسب ندارند.** وضعیت تسک (۱ تا ۴)، ریسک، مایل‌ستون، هزینه (۱ تا ۴)، Playbook و اولویت‌ها در schema فقط عددند و معنای هر عدد مشخص نیست. پیشنهاد: `x-enum-varnames` یا توضیح در schema. پروتوتایپ فرض کرده:
   - وضعیت هزینه: ۱ برنامه‌ریزی‌شده، ۲ در انتظار تأیید، ۳ تأییدشده، ۴ پرداخت‌شده.
   - وضعیت پروژه: ۱ سبز، ۲ زرد، ۳ قرمز.
2. **پاسخ‌های گراف وابستگی تایپ درستی ندارند.** در schema، پاسخِ `task-dependencies/graph/` و `task/{id}/predecessors|successors` از نوع `TaskDependency` (یک شیء تکی) ثبت شده. پیشنهاد برای `graph`: `{nodes:[{id,title,status,assigned_to,start_date,due_date,progress}], edges:[{id,predecessor,successor}], critical_path:[...]}`.
3. **وابستگی نوع و فاصله ندارد.** فقط `predecessor` و `successor` دارد. پیشنهاد: `type` (FS/SS/FF/SF) و `lag_days`. سرور باید حلقه را رد کند (پروتوتایپ رد می‌کند) و تعارض تاریخ را برگرداند.
4. **فیلدهای تسک برای سند ناکافی است.** این فیلدها وجود ندارند:
   - `description`، `labels` و `checklist`
   - `estimated_budget` و `estimated_hours`
   - `milestone_id`
   - `comments` (endpoint جدا)
   - `attachments`

   ستون‌های سفارشی بورد و `blocked` هم نیاز به مدل `BoardColumn` (نام، نوع، ترتیب، WIP) دارند.
5. **هزینه به تسک وصل نیست.** `task_id`، `description`، `receipt` و `created_by` ندارد. بدون `task_id` کنترل هزینه‌ی هر تسک (بند ۸ و ۳۰ سند) ممکن نیست.
6. **ریسک ناقص است.**
   - `impact` و `task_id` ندارد.
   - `responsible` رشته است، نه شناسه‌ی کاربر، و بدون شناسه نمی‌شود به مسئول اعلان داد.
7. **مایل‌ستون** مسئول (`owner_id`) و تسک‌های مرتبط ندارد.
8. **جلسات فقط شکل صورت‌جلسه را دارند.**
   - `attendees` بدون تایپ است.
   - ساعت، نوع (حضوری/ویدیویی)، وضعیت (برنامه‌ریزی/برگزار/لغو) و تسک‌های مرتبط وجود ندارد.
   - متن تصمیمات و Action Itemها (با مسئول و سررسید، قابل تبدیل به تسک) هم نیست.
9. **بخش‌هایی از سند که endpoint ندارند:**
   - مشکلات (Issues)
   - ثبت زمان (Time Tracking؛ `gantt` فقط `total_spent_seconds` دارد)
   - اسناد پروژه
   - کانال‌ها و اطلاعیه‌های پروژه
   - تقسیم بودجه بین سرفصل‌ها و درآمد
   - قالب پروژه (Project Template)
   - بایگانی و ستاره‌دار کردن
   - نقش عضو در پروژه (مالک، مدیر پروژه، عضو، مشاهده‌گر)
   - اعلان‌ها و قواعد اعلان
10. **مشکلات نام‌گذاری و بدنه‌ی درخواست:**
    - مسیرهای `Addmembers` و `RemoveMembers` با حروف بزرگ نوشته شده‌اند؛ پیشنهاد: `members/add` و `members/remove`.
    - `execute` در Playbook بدنه‌ی `PlaybookTemplateRequest` می‌گیرد، که باید `{project_id}` باشد.
    - `cancel`، `complete` و `skip` بدنه‌ی `PlaybookExecutionDetailRequest` کامل می‌خواهند، که باید `{notes}` باشد.
11. **شناسه‌ها یکدست نیستند.** `owner_id` در `Project` عدد است ولی در `PlaybookTemplateList` از نوع uuid است. `assigned_to` هم در `TaskList` عدد است ولی در `GanttTask` از نوع uuid.
